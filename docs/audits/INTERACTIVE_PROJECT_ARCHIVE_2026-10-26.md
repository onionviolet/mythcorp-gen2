# An interactive project archive for MYTHCORP

October 26, 2026. Research and proposals only. No design selected, prototype built, application code changed, site unlocked, commit, push or deployment.

## Recommendation

**O1: Test a small object archive that opens direct, readable project stories.** Give the archive a little of evanciao's handmade physical character: a faceted object, a purposeful arrangement, an image that feels personally made. Let selecting an object reveal something about the project. Keep its name, short description and ordinary link visible before interaction. Use the same project story whether someone enters through an object or a shared URL.

This is the best candidate for a distinctive archive, not a decision to replace the front page. MYTHCORP already has an installation, rooms, a specimen, a cat and a console. The project archive should add a reason to explore those surroundings, not another fictional employer or a new character everyone must meet. Start with Gandalf and OOPS as requested content. Future projects should need content and one image, not another modeled room.

**A1: Recommended next action, requiring a separate implementation request:** compare one complete Gandalf story in a three-object cabinet with the identical story on a direct editorial page. The bounded brief and adoption gate below make that decision observable. No public inference is needed for the comparison.

## Five directions, ranked for this archive

Ranks are judgments about these projects and this existing site, not universal quality scores. Cost is relative implementation and ongoing authoring effort, not an estimate in hours.

| Rank/code | Direction and first 30 seconds | What the visitor causes | Growth, access and cost | Verdict |
|---|---|---|---|---|
| 1 / O1 | **Exploratory object archive plus readable stories.** A small shelf/cabinet shows named project artifacts, their plain purpose and status. Selecting one opens the project story. | Select a project or open one meaningful layer: example, mechanism, changes. Discovery adds context without hiding the name. | Moderate cost with still/SVG/CSS objects and real links; same data can produce a vertical phone list. Adding a project uses an image and metadata. URLs and ordinary text remain primary owners. | **Adopt as the leading prototype candidate.** It offers the desired place-like quality while fitting the specimen/workshop identity. Adapt Getty's reveal and UNFOLD's provenance, not their surfaces. |
| 2 / O2 | **Editorial story with a working proof control.** First screen states the project, shows its artifact and offers one clear action. | Step a defense or change a constrained input; compare the result with an explanation alongside it. | Lowest-to-moderate cost, strongest direct-link and reading experience. New projects reuse the story pattern, although each meaningful proof still needs design. Native controls work for touch/keyboard; motion can be optional. | **Adopt as the content foundation and comparison baseline.** Distinctiveness comes from the proof itself and personal artifact, not a decorative portfolio grid. |
| 3 / O3 | **Low-poly diorama or fixed desk.** One camera, a few labeled objects, one selected project. No avatar movement required. | Select an object; a bounded camera move or layer reveal exposes the same project story. | Highest art/load cost of the shortlist. Future projects must fit reusable plinths or printed labels; otherwise bespoke scene work grows with every addition. Needs DOM links, a still image and a phone/list mode. Low polygon count alone does not establish low transfer or GPU cost. | **Adapt and test only if the object comparison earns it.** Use original faceted props and restrained textures. Skip a walkable island, puzzle locks, forced camera travel and mandatory sound. |
| 4 / O4 | **A small playable system per project.** Gandalf asks one question about a defense; OOPS could later expose one bounded craft/progression decision. | Make a prediction or choice, see a consequence, reset and compare. | Moderate cost initially, potentially high maintenance if it duplicates game logic. Finite local scenarios can use buttons and immediate nonanimated results on phones. Free-form public AI introduces a separate service. | **Adopt selectively inside O1/O2.** Best when play teaches one true behavior. A decorative falling-object toy does not explain Gandalf or OOPS. |
| 5 / O5 | **Old-web desktop or terminal archive.** Named files/windows or a small personal homepage cluster, with visible clickable destinations. | Open a named file, run an optional suggested command, or follow a related note. | CSS chrome can be cheap; window dragging, stacking, persistence and mobile management are not. Terminal-only navigation hides work from visitors who do not know commands. | **Adapt a light file-browser surface or extend existing Console links later.** Skip a second OS, fake boot wait, tiny retro text and mandatory command entry. ## More to consider: constraints that change the design

**ACCOUNT FOR NOW** means constraints on a later design, not authorization to implement it.

| Code | Consequence | Disposition |
|---|---|---|
| R2 | Three objects can mean three projects or three aspects of one project. Mixing those meanings makes the cabinet harder to read. | Prototype three clearly named Gandalf aspects. A later archive uses project objects; its project page may expose aspects. Do not require a permanent three-project lineup. |
| R3 | A mascot adds rigging, reactions, identity and asset obligations. MYTHCORP already has specimen/cat attention cues; docent plus morphing plus a new archivist would compete. | No new mascot in the first comparison. The desktop companion in `Project_Brainstorm.md` section 4a remains independent. Shared original character art is an optional later reuse, not a dependency or accepted design. |
| R4 | Heavy navigation can delay the story before any project is opened. A small polygon count does not cap textures, postprocessing or JavaScript. | Render names, status and story links first. Load diorama/game/video only on explicit activation; pause/unmount hidden stages. Reuse the existing one-canvas discipline. |
| R5 | Keyboard focus, touch targets and URL state are harder to retrofit than a still fallback. A screenshot cannot replace explanatory text for a screen reader. | Semantic links/buttons, visible focus, at least 44px touch targets, no hover-only labels, no drag-only action, Escape/close and focus return. Keep selected project/aspect in a normal route/hash/query and test reload, Back and direct entry. |
| R6 | Reduced motion and WebGL failure are different conditions. A quiet layout should still explain the project. | Reduced motion removes camera flight, orbit and idle motion; selections update immediately. No WebGL/failed asset gives a labeled still and the same DOM story. A phone can use a vertical object list without being called a degraded experience. |
| R7 | A demo can drift from the app, especially if a proof control reimplements current mechanics. | Keep a dated captured example or named fixture, source/build identifier and one owner to refresh it when the relevant feature changes. Prefer a small standalone illustration to a second game engine. No automatic weekly freshness promise. |
| R8 | A page lock is not protection for everything in a deployed artifact. `isRequiredSiteRequest` permits static file requests and APIs. | Keep private material out of `public/`, bundles, maps, screenshots and metadata even while a page is held. Noindex is not publication approval. Allowlist changes and any external demo release remain separate decisions. |
| R9 | Attribution and disclosure can vanish when a playful overlay closes. Cross-site hosting also loses navigation context and may have a separate availability state. | Keep credits, demo type, dated status and repository links in the reading page itself. Link out explicitly; provide a transcript/still if the external service fails. Borrow mechanisms, not source art/branding/compositions. |
| R10 | Early research, installed code, committed source and public releases are different states. An archive often flattens them into one ambiguous "live" badge. | Give each project a dated state and precise action labels: watch recording, try illustration, open demo, read source, run locally. Keep process notes personal and direct; no fictional corporate reports or unrelated career story. |

**LATER:** A before/after revision view, an annotated failed attempt, or a linked making-of note could add more meaning than a fourth animation. Use one when real evidence exists. Do not build a discovery counter, shared character system, full desktop or public model backend as a dependency of the archive.

## Bounded one-project prototype comparison, not built

**P1 Question:** Does a three-object cabinet make Gandalf more memorable without making its purpose, demo type or setup harder to find than a direct page?

| Arm | Contents and behavior |
|---|---|
| P1-A, direct editorial baseline | Gandalf title, unofficial learning-game description, dated state, one scripted defense comparison, explanation, changed-by-Weibao note, limits, credits and setup/repo links in one page. Aspect links jump to Example, Defense and Setup. |
| P1-B, object cabinet | Identical copy, examples and links. Three original still/CSS/SVG objects labeled Example, Defense and Setup select those exact aspects. The project title/purpose stays visible. Selecting an object reveals its corresponding story section and updates an addressable fragment; ordinary links offer the same route. No mascot, game navigation or animation required. |

P1-B can use a faceted desk illustration to audition low-poly art direction without requiring WebGL. A real 3D version is a later O3 experiment only if the cabinet structure helps. Keep both arms as private `/og` studies with DraftBanner and the existing lock. Suggested route names are proposals; creating them is not selected.

Use a fixed fictional word, two or three authored responses, and the exact-match rule to illustrate literal versus indirect disclosure. Label both arms "Scripted illustration, no live AI" near the control. Show the outcome and explanation immediately on selection. A later real recording is separate evidence, not something this prototype pretends to generate.

**P2 Observable acceptance gates, proposed targets rather than measured results:**

| Gate | Check and decision rule |
|---|---|
| P2.1 Comprehension | Counterbalance arm order with at least five unfamiliar visitors if available. After 30 seconds, at least four can explain the project's purpose, identify the illustration as scripted and find local setup. Cabinet must not trail the direct page on any of those three counts. Without visitors, record comprehension as unverified, not passed by agent judgment. |
| P2.2 Navigation and recall | Record time to find Defense and Setup; cabinet median must be within 5 seconds of baseline. After closing the page, ask which defense example they remember and which presentation they prefer. Prefer the cabinet only if at least three of five prefer it, it retains the comprehension gate, and task finding does not worsen beyond the threshold. This is a small directional study, not statistical proof. |
| P2.3 Access and recovery | At 1440x900 and 390x844, keyboard and touch complete every action without hover/drag; no horizontal overflow. Check 200% text zoom, visible focus, close/focus return, blocked storage, Back, direct fragment reload, JS-disabled reading and failed art loading. Reduced motion preserves every result with no automatic travel. Test all four themes and both plain schemes on an open local preview, then verify held behavior separately. |
| P2.4 Load boundary | Before activation, zero new GLB, game bundle, model-service call or video download. On the same device/network, measure each arm's incremental compressed transfer and first readable render. Proposed ceiling: cabinet adds at most 150 KB over baseline before activation and delays readable content by no more than 300 ms. Adjust the art or choose baseline if it fails. These are study budgets, not existing site measurements. |
| P2.5 Growth and maintenance | Add one dummy future entry locally from title, purpose, dated status, image/alt, story and links. It must appear usefully in archive and phone list without new geometry/layout code. Verify the example's fixture/source date and credits are present. Remove the dummy before any promotion. |

**D1 Proposed adoption rule:** choose P1-B only if it clears the access/load gates and earns the navigation/comprehension result. Otherwise retain O2 and reuse the best cabinet art as a still. Do not proceed automatically to 3D. The archive's future public release still requires an explicit publication/unlock decision, regardless of prototype results.
